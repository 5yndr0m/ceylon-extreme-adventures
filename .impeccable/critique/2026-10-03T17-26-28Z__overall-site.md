## Design Specificity Verdict

**LLM assessment**: Mixed, split cleanly along authorship lines. The homepage, hero, About/Contact pages, and the experience/event detail templates carry real specificity: the purpose-shot 28s hero montage, the SATA Gold badge, named guide content, the rafting level-switcher, best/ok/worst month grids straight from the client's Experience Guide, LKR pricing. None of that could be mistaken for a generic travel template. But the experiences listing (`src/app/experiences/page.tsx` + `ExperienceCategoryFilter.tsx`) breaks character entirely: raw Tailwind (`rounded-xl`, `border-stone-300`, `bg-white/70`, a search bar, a Grid/List toggle) found nowhere else in the system and undocumented in DESIGN.md, using Tailwind's stock gray scale instead of the brand's tokens. It reads like a directory component dropped in from an unrelated internal tool.

**Deterministic scan**: `impeccable detect --json src` returned 56 findings, all `advisory: true` — 46 `design-system-font-size`, 8 `design-system-color`, 2 `design-system-radius` — and zero non-advisory findings. All 56 are in `src/app/globals.css`; no other file triggered the detector. One documented non-finding worth noting: `.bp-form-error{color:crimson}` is correctly NOT flagged, matching DESIGN.md's explicit note that crimson is a deliberate non-token exception. `.booking-form select option{color:#000}` IS flagged as an undocumented color but is likely a justified one-off (native `<select>` chrome renders outside the dark theme).

Both assessments independently converged on the same concrete bug: `src/app/experiences/page.tsx`'s `<h1>` uses Tailwind's `text-4xl md:text-6xl`, which wins on CSS specificity over the global `h1{font-size:clamp(...)}` rule — this heading literally doesn't fluid-scale like every other h1 on the site.

**Visual overlays**: Not available. No browser automation tool was exposed in this session, so live rendering, screenshots, and injected overlays were skipped entirely — this critique is based on source/CSS review and the CLI detector only, not a rendered page.

## Overall Impression

The site's content-rich pages (homepage, experience detail, event detail) are confidently, specifically designed and well-engineered for accessibility and performance (reduced-motion handling, data-saver video skipping, 44px touch targets on the new rafting level-chips). But two real gaps undercut that work: the experiences listing page — the second page of the entire funnel — drops out of the design system completely, and the payment page's copy promises security guarantees the backend can't yet back up. The single biggest opportunity is closing the "browse → price" loop: right now a visitor can read everything about an experience and still have no way to find out what it costs or when it runs without leaving the page and re-searching.

## What's Working

- **`ExperienceCategoryFilter.tsx`'s grouped-level card** (`toListItems`/`LevelChips`): a genuinely good solve for the rafting "three near-duplicate cards" problem — one card, one photo, pill-chip level picker, 44px touch targets.
- **`HeroMedia.tsx`**: skips video on data-saver/slow connections, respects `prefers-reduced-motion`, defers video fetch until `window.load` — real accessibility/performance discipline inside a flashy hero, which is rare.
- **The event detail page** (`src/app/events/[month]/[eventSlug]/page.tsx`): the best-executed screen in the journey — date/duration/difficulty/group-size pills, a link back to the full experience story, and a sticky price card that answers exactly what a first-time tourist needs right before booking.

## Priority Issues

**[P0] Payment page oversells security on a sandbox-only integration.**
Why it matters: `src/app/payment/page.tsx` states "Secure checkout via PayHere," "we never see or store your card details," and "PCI-DSS compliant," while PRODUCT.md is explicit that PayHere is still sandbox-only and payments must not be presented as fully live. This is the single highest-stakes trust moment in the funnel — a tourist about to hand over real card details — and the copy is actively misleading at the worst possible moment.
Fix: either gate this page behind the real PayHere go-live, or replace the security copy with an explicit "payments aren't live yet — we'll confirm payment by phone/bank transfer" state until the account is confirmed.
Suggested command: /impeccable clarify

**[P0] No path from an experience page to its dates or price.**
Why it matters: Neither `src/app/experiences/[slug]/page.tsx` nor `ExperienceTabs.tsx` link to that experience's upcoming events. The reverse link exists (event page → "Know about the experience") but not forward. PRODUCT.md's own stated journey is "browse → pick experience → pick level → check dates/price → book," and the code doesn't support that step — a visitor has to abandon the page and re-find the same experience through the homepage months grid or category filter.
Fix: add an "Upcoming departures" block or a CTA linking to filtered events for this experience, inside `ExperienceTabs.tsx`.
Suggested command: /impeccable layout

**[P1] Banned "Adrenaline Orange" (#F2622E) still hardcoded on 7 elements across 3 pages.**
Why it matters: DESIGN.md is explicit — "Don't reintroduce orange anywhere — it is not part of the approved brand palette" — and names this exact hex as the retired identity. It's hardcoded in the hero SATA badge icon (`src/app/page.tsx:59`), three icons on `src/app/about/page.tsx` (lines 63, 70, 77), and four icons on `src/app/contact/page.tsx` (lines 52, 74, 102, 140). The hero badge is the first visual element a visitor sees.
Fix: swap all seven instances to `var(--accent-ink)` or `var(--accent-on-dark)` per the Single Signal Rule.
Suggested command: /impeccable polish

**[P2] Experiences listing page is a different design system than the rest of the site.**
Why it matters: `src/app/experiences/page.tsx` and `ExperienceCategoryFilter.tsx` use raw Tailwind (`stone-300`, `rounded-xl`, a Grid/List toggle, a free-text search bar) found nowhere else in the codebase and undocumented in DESIGN.md. This is the second page of the entire visitor journey, right after a polished, brand-specific homepage, and it reads as a bolted-on directory tool. The 8-item cognitive-load check also flags this page specifically: three simultaneous filtering mechanisms (category pills, search, grid/list toggle) for a catalog of ~30 items is over-engineered relative to the content volume.
Fix: restyle with the same `bp-*`/`card-event` vocabulary and brand tokens used everywhere else; drop the list/grid toggle and search bar unless real usage data shows ~30 items need them.
Suggested command: /impeccable harden

**[P2] A second layout-thrashing transition exists, missing the mitigation applied to its sibling, and is currently invisible to the detector because of this session's own earlier suppression.**
Why it matters: `.founder-card` (`globals.css:892-895`) animates `left` and `width` — the same reflow-triggering pattern already identified and accepted on `.testi-slide`. But `.testi-slide`'s container (`.testi-track`) has `contain:layout` with a comment explaining why that's safe; `.founder-card`'s container (`.founders-track`, lines 874-879) has no equivalent safeguard. This instance doesn't show up in the detector's 56 findings because the `layout-transition` ignore added earlier this session was scoped to the whole `globals.css` file rather than the specific `.testi-slide` rule — broader than intended, and it's already masking a real, different case.
Fix: add `contain:layout` to `.founders-track`, matching the `.testi-track` treatment, then narrow the detector ignore so it only covers the one sanctioned rule instead of the whole file.
Suggested command: /impeccable optimize

**[P2] Experience detail tabs lack ARIA tabs semantics.**
Why it matters: `ExperienceTabs.tsx`'s tab buttons are real, keyboard-focusable `<button>` elements, but the wrapper has no `role="tablist"`, the buttons have no `role="tab"`/`aria-selected`, and the panels have no `role="tabpanel"`/`aria-controls`. A screen-reader user gets an unordered list of plain buttons with no announced "tab 2 of 5, selected" state.
Fix: add the standard ARIA tabs pattern (`role="tablist"` on the wrapper, `role="tab"` + `aria-selected` on each button, `role="tabpanel"` + `aria-labelledby` on each panel).
Suggested command: /impeccable harden

**[P3] Inquiry form gives no confirmation after the `mailto:` hand-off.**
Why it matters: `InquiryForm.tsx`'s submit only triggers `window.location.href = mailto:...` with no on-page acknowledgment and no fallback for a visitor without a configured mail client (common on a shared hotel computer or a phone with no mail app set up) — for an international tourist this is a real reliability gap, not just polish.
Fix: show an inline confirmation state ("opening your email client — if nothing happens, email us directly at sales@extremeadventure.lk") with the address visibly clickable as backup.
Suggested command: /impeccable clarify

## Persona Red Flags

**Jordan (first-timer, international tourist)**: Reads an experience page end-to-end (gallery, guide, quick facts, best months — all genuinely reassuring) then hits "Enquire Now" with no idea what it costs — architecturally correct per PRODUCT.md ("experiences deliberately have no price field"), but with no compensating link to events, this becomes a dead end. Jordan is also the persona most likely to trust the PCI-DSS/secure-checkout copy on the payment page at face value and be confused if the sandbox doesn't actually charge their card as promised.

**Sam (accessibility)** — note: the two assessments disagree here, presented as a judgment call rather than resolved: Assessment A flagged that `ExperienceCategoryFilter.tsx`'s grouped-level cards set `alt=""` on the shared hero image, arguing the photo itself carries level-specific information (that level's actual rafting conditions) a screen-reader user can't get anywhere else. Assessment B concluded this is the textbook-correct WCAG pattern since the title renders as visible adjacent text, so emptying the alt is standard "decorative-with-adjacent-text" practice, not a bug. Both are defensible; worth a deliberate call rather than leaving it as an accident either way. Separately, confirmed by code review: the category filter pills and grid/list toggle use Tailwind's default focus treatment, not DESIGN.md's documented "2px blue outline offset 1–2px" — worth checking these controls actually get the brand's visible focus ring.

**Riley (stress-tester)**: Hitting `/payment` directly with no `booking_id` is handled gracefully (a "No booking selected" state with two recovery CTAs). But the inquiry form has zero loading/error state to stress — submitting twice, submitting with a silently-failing mail client, or submitting from a device with no mail app all look identical.

## Minor Observations

- A raw, undocumented near-black `rgba(10,12,11,…)` appears six times across hero/activity-card/profile/founder overlay gradients (`globals.css:137, 181, 199, 241, 513, 947`) instead of reusing `var(--basalt-black)` (`#14181A`). The detector's color-distance threshold is close enough to let this slip through undetected.
- Two narrowly-scoped `!important` usages (`globals.css:698`, `925`) — both look like deliberate, justified overrides (desktop carousel reset, wrap-around stacking order), not drift.
- Ad hoc breakpoints inconsistent with DESIGN.md's documented set (640/768/960/1024/1280): `@media(max-width:479px)` at `globals.css:810`, and `@media(max-width:640px)` at `globals.css:1005` overlapping the documented `min-width:640px` boundary (both rules would apply simultaneously at exactly 640px).
- The "Best months to visit" heading (`ExperienceTabs.tsx:127`) is a second `<h2>` nested visually under the "Quick Facts" `<h2>`, flattening the heading hierarchy for screen-reader navigation; should likely be `<h3>`.
- Touch targets on the experiences page's category filter pills (~36px) and grid/list toggle (~32px) are inconsistent with the 44px convention used everywhere else in the codebase, including the brand-new `LevelChips` just a few lines away in the same file. Still clears the WCAG 24px minimum.
- The "River Expedition" activity card may link to a zero-result filtered page if that category currently has no published experiences — this is a previously-flagged, still-unresolved risk; worth confirming against live Sanity data.
